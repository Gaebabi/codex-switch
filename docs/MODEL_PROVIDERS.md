# Configurable model providers

Normal Codex connects directly to OpenAI and works with Switch completely stopped. The combined desktop profile is retired because it routed native requests through Switch. Existing installations use **Settings > Codex profile > Default — restore and restart** before preparing the separate custom CLI profile below. The apply-Switch action is no longer available. [Native restoration and history preservation](DESKTOP_MODEL_PROFILES.md).

Provider support is available in the1.43.3release. The isolated custom-profile architecture below is an unreleased source change after1.44.0; existing release downloads retain the earlier shared connection. Windows/shared-desktop compilation,303 provider/native contracts and139 offscreen UI checks pass. Real terminal/UI acceptance and external-provider compatibility remain separate. [Issue138](https://github.com/Gaebabi/codex-switch/issues/138) tracks provider acceptance.

New connections leave native Codex's root configuration, model catalog and default untouched. Custom models run in a separate, explicitly launched CLI process with the V2 `codex-switch` profile. Its custom-only catalog contains the fixed aliases of registered Responses models and a hidden legacy `codex-switch` entry; this separate CLI workflow adds nothing to the normal desktop picker. Switch’s sliders popup controls each model’s visibility. The client selects a fixed alias per chat. Only legacy-ID requests use the saved global selection. Each admitted request retains its model, destination, key and reasoning default through its response and bounded retries; list edits never retarget an in-flight stream. A duplicate turn request is refused rather than replayed against a newly selected backend.

## Set up a provider

1. In1.44.0, open Model providers in the titlebar Settings gear. Older1.43.3 Windows packages use Models in the toolbar.
2. In the first step, select Add a provider or a saved provider, then enter its display name, API base URL and API key. Choose Save and continue to discover and save its models.
3. For a large catalog, expand the optional model-ID field and enter one ID per line. Leave it empty to discover all models within the supported bounds. Reasoning and conversation-handoff controls stay under Advanced in the second step.
4. In the second step, configure model visibility with the sliders icon, then connect to prepare the custom profile. This requires a reviewed official CLI version0.167.0 or newer with V2 profile support. Connecting does not restart Codex or change its root default. Saving or toggling alone does not connect.
5. Use **Open custom terminal**, or copy and run the displayed command, equivalent to `codex --no-daemon --profile codex-switch` with the verified executable and existing Codex home. Keep Switch running for custom requests and choose a fixed custom model in that terminal's model picker. Model edits are saved immediately to its separate static catalog; reopen the terminal to load the updated list and capabilities. This does not change the normal desktop picker.

The encrypted provider store retains the legacy default selection. An unavailable/deleted route fails before inference; Switch never silently selects another destination for an existing chat. Use a registered fixed alias in the client's model picker and normal Codex for native OpenAI models. Stopping Switch leaves normal/native Codex independent; custom requests fail while Switch is offline. Legacy custom aliases and saved histories are preserved. A legacy installation migrates only through an explicit Connect action. A native process that already loaded an older root override may need the owner's normal restart after restoration to discard its in-memory routing; connection and verification never automate that restart.

Saved providers reopen with their fields and a masked key. The eye button shows or hides the current key, and Copy copies it only after an explicit click. Neither action changes the key. Changing the destination URL still requires an explicitly entered replacement key; displaying a saved key does not authorize sending it elsewhere.

Draft fields and the last selected provider are encrypted in the existing model-providers.vault when changing providers, attempting a save or closing the editor. A failed save retains the input. More options offers Load saved values, Use these values for a new provider, provider removal and connection restoration. Loading saved values is the explicit way to discard an edit. The account vault and original OpenAI login are preserved.

The model setup action opens only the custom terminal, with a copy-command fallback. The unrelated account restart/recovery flow remains separate; preparing or launching this profile does not invoke it or submit Continue to existing chats.

The launch command pins the executable path and SHA256 recorded during profile preparation. A changed CLI requires preparation again. Credential and endpoint environment overrides are removed only from the child process; the parent shell environment is preserved. The profile uses the existing file-backed official sign-in and does not copy authentication. Windows opens a separate terminal; Mac/Linux currently provide the POSIX command-copy fallback.

Existing custom histories remain untouched. Resuming one requires its compatible custom profile and backend; an old desktop chat that still names `codex-switch` does not become a native model after restoration. Desktop-only automatic Continue and account-switch resumption are not established for the dedicated CLI. No history or encrypted context is migrated or rewritten.

Common full endpoint URLs ending in /chat/completions, /responses, /responses/compact or /models are normalized to their API base without changing the server. For OpenRouter, the base is https://openrouter.ai/api/v1.

Legacy migration restores only exact root values previously applied by Switch through the official configuration RPC with `expectedVersion`. Values already equal to their saved originals are accepted; any other divergence is refused rather than overwritten. Unrelated settings/comments are preserved, and encrypted original/applied receipts remain in the provider vault for recovery. Disconnecting the isolated connection removes only its verified owned profile configuration, not the normal Codex default or histories. An externally edited profile is refused rather than overwritten.

## Compatibility and history

The local gateway supports full-input HTTP Responses replay. If the official client first attempts a WebSocket upgrade, Switch returns426 so that client chooses HTTP before inference. A missing upstream Content-Type does not change a requested streaming summary into JSON: Switch reads SSE and requires `response.completed`. Explicit JSON summaries remain supported; other declared formats and incomplete streams fail without dropping context.

The custom endpoint must implement Responses streaming, tools and follow-up conversations. A Chat Completions or Anthropic Messages endpoint alone is insufficient. HTTPS is required, with HTTP allowed only for loopback services.

A provider's native Codex catalog retains its model instructions and capabilities. A plain OpenAI-compatible model list receives conservative text-only settings and the attributed Codex generic fallback instructions. Isolated mode does not fetch the signed-in account's native OpenAI catalog or infer capabilities from an OpenAI-like name. Configure explicit reasoning metadata when the provider does not supply it. [Fallback attribution](../licenses/OpenAI-Codex.NOTICE.txt).

### GPT reasoning controls

Use Codex's existing reasoning control beside its model selection. The single Switch entry advertises the selected model's metadata levels, descriptions and default. A supported selected effort is forwarded unchanged; a saved/provider default applies only when no effort was supplied. Model selection and metadata edits update only the owned Switch entry's reasoning fields, preserving its model ID and all native OpenAI documents. The destination must support the declared values; matching IDs do not certify external provider behavior.

The current Codex client caches configured JSON catalogs in memory. Updated ranges appear after a normal client reload, using the existing same-account apply-and-restart flow when ready. Saving or selecting a model does not silently restart active chats. A stale unsupported effort is refused before inference instead of being replaced with a different strength. No extra slider is added to the Switch window.

For a model without provider reasoning metadata or a route with different support, expand **Model reasoning**, select the saved model, enable **Set supported reasoning levels**, select its documented levels and a default, then save. Disable the override and save to return to provider metadata. These settings apply to one model and remain after rediscovery at the same destination. A changed destination resets them. An existing native selection is retained when supported; changing the saved default does not override an explicit native choice. Reload Codex to show changed capability ranges.

Supported control values are `none`, `minimal`, `low`, `medium`, `high`, `xhigh` and `max`, subject to the installed Codex version and the model's API. Unsupported selections fail before inference rather than silently using another strength. A plain list without provider metadata or explicit settings keeps provider-default behavior. No additional reasoning API or token-budget conversion is used.

Switch supports at most32 providers and128 selected models per provider. Discovery reads are bounded at4MiB; the complete Codex-facing catalog must fit the client's1MiB limit. Full-input conversation and image requests are bounded at512MiB, including chunked bodies. Request buffers share a1GiB capacity budget, with64MiB reserved for small requests and resize overlap included. At most eight bodies larger than16MiB or of unknown length upload concurrently, within16 upload/routing slots. Up to48 upstream responses can stream concurrently; successful streams do not occupy upload slots. Local overload reports503 with `Retry-After: 1` and is never retried internally. Above-limit bodies report413; unsupported media types report415. Upstream limits still apply. A discovery result alone does not certify tool or conversation compatibility.

JSON validation reads tokens without a payload-sized document metadata pool. It refuses duplicate properties, nesting above64levels, more than one million tokens, property names over1KiB or total property-name bytes over8MiB. Routing controls (`reasoning` and `text`) are each limited to64KiB. These bounds apply before upstream inference and do not remove conversation items. Custom-provider rewrites serialize only small controls and stream original history/image value slices. Historical shared-mode OpenAI forwarding retains exact body bytes, but is refused in isolated mode. The buffer budget covers request arrays, not all process/runtime/HTTP allocations.

Changing providers sends replayed readable conversation to the selected provider. Provider-encrypted reasoning is omitted after a conversation crosses routes; hidden reasoning is never decrypted or summarized. Compressed history now has a portable gateway checkpoint path described below. Stateful response references are still refused rather than silently dropping history.

The connection uses existing file-backed OpenAI authentication. The local listener accepts authenticated requests on127.0.0.1 only, refuses browser-origin requests, and never forwards an OpenAI credential or account header to a custom provider. A custom provider receives only its saved key. Redirects are not followed. The only automatic inference retry is the explicit HTTP507 recovery described below.

For Codex requests carrying the native turn identity, the gateway retains a hashed receipt for each distinct input and route for30minutes. Automatic client retries of that same turn request are refused before another upstream send; a new user turn or changed full-input tool follow-up remains eligible. The receipt budget is4096 and a full budget reports503. Receipts contain no request body or credentials and last only for the current gateway process. This prevents the built-in client's retry policy from multiplying the gateway's own recovery budget.

### Automatic HTTP507 recovery

For streaming `POST /responses`, an upstream HTTP507 refusal before its response begins is retried at most three times, after2,5and10seconds. The original attempt plus retries makes at most four upstream requests. All attempts retain the original selected model, provider URL/key, signed-in account, complete input bytes/history and tool-call identities. The current sign-in is revalidated before another attempt. There is no new chat, `Continue` message, model/account change, history trimming or context compression.

While waiting, Switch sends only SSE comment keep-alives to the original caller. These are not assistant messages or model response events. Successful upstream events continue in the same request. After exhaustion or a different upstream failure, Switch emits one terminal `response.failed` event with the HTTP status and retry count; upstream error bodies are never echoed. Success alone records conversation provenance. The total request deadline remains30minutes, and request arrays remain within the existing aggregate buffer/admission limits until retry eligibility ends.

### Continue after a failed response stream

The desktop observer below is an existing, separate capability. It does not establish automatic failed-turn continuation for the custom CLI process, which has no desktop owner. Opening the custom terminal never adopts desktop chats or triggers that observer's Continue flow.

A later hotfix observes confirmed desktop turn failures of every error type, including HTTP507exhaustion, invalid event streams, authentication, quota and context errors. Eligibility uses the persisted failed status, without matching error words or requiring an error message. After the original turn has stopped, Switch can send one identified `Continue` through that chat's existing desktop owner, inheriting its settings. It does not replay the original Responses input after tools or partial output may already have run. Consecutive failed automatic continuation turns share at most three attempts, with3/10/30second backoff; successful completion closes that recovery chain. This is separate from the pre-response HTTP507request budget, so each new continuation has its own bounded HTTP507retries. A persistent error can still require user action after all three continuations fail.

The observer requires a recent persisted `task_complete` failure, an observed stopped main chat with no approval/input/queued follow-up, matching current model/provider, a connected original OpenAI/Switch provider and unchanged current sign-in/route during backoff. Custom model aliases and the virtual model's selected actual route must still be registered. An earlier successful request is not required: the first request can fail before successful-route history exists. This never fabricates route history or bypasses encrypted-compaction and portable-history checks in the gateway. It skips active, completed, interrupted, paused/limited-goal and unsupported-provider chats. The bounded read-only rollout tail comes from the existing SQLite thread record; a newer `task_started` invalidates a historical failure. No original transcript is rewritten, no account or model is changed and no window is opened or activated.

Encrypted recovery receipts persist attempt count and message/turn identities before submission. A lost/ambiguous IPC response or persistence error stops that recovery rather than resending. Exhaustion survives a Switch restart. Reauthentication, route edits, new user turns, queues and actual user interruptions prevent resubmission. Generic idle/EOF alone does not establish a failed turn. The observer applies only to chats observed in this local desktop with a connected OpenAI/Switch provider; it does not revive archived or unloaded historical chats. The local `stream-recovery-state.json` also retains up to128deduplicated decisions with fixed reason codes, hashed chat/turn references and attempt counts. It omits chat text, raw errors, account identities and provider secrets.

Cancellation, a disconnected client, sign-in changes, gateway shutdown, transport exceptions and any failure after a successful upstream response stop recovery. Images, compaction, nonstream requests and other HTTP errors retain their single-send behavior. A manual new send has a new bounded budget. An already failed turn from before this hotfix needs one manual resume; the gateway does not scan old chats or submit work on its own. This recovery cannot guarantee that a server-side507condition clears and does not prove an upstream performed no internal work.

In the isolated profile, native OpenAI text routes and built-in `images/generations` / `images/edits` routes are explicitly refused. Use normal Codex for native text and image generation; those requests must not depend on Switch. Custom text models may receive image attachments only when their declared capabilities support them. The older shared gateway's native-image passthrough described in historical hotfix evidence is not the isolated-profile contract.

The image-route and 64MiB corrections are source hotfixes after release1.43.3. Older packages can report an unsupported-endpoint404 for the built-in image tool, or `A bounded JSON Responses request is required` when a full-input conversation exceeds16MiB. The hotfix does not remove conversation history to make it fit. [Verification and delivery scope](evidence/image-gateway/README.md).

A subsequent source correction raises the64MiB intermediary limit to512MiB because an image-heavy full-input chat can exceed it. The [OpenAI image input guide](https://developers.openai.com/api/docs/guides/images-vision?api-mode=responses) documents up to512MB total payload for the public API; authenticated Codex and custom upstream acceptance must be verified separately. This change preserves image data and encrypted history and does not silently compact or discard them.

The large-upload admission slot and request buffers are released when final upstream response headers arrive, so ongoing response streams do not occupy large-upload capacity. Explicit retryable507refusals retain the same budgeted input until the next attempt or terminal failure; they never allocate a second full body.

Unregistered model names fail explicitly. Isolated mode accepts the virtual model and registered custom aliases, never native OpenAI fallback. Managed provider/catalog requirements are refused before preparing a local connection.

Connect writes `<Codex home>/codex-switch.config.toml`, a V2 profile containing `model_provider = "openai"`, `model = "codex-switch"`, the loopback `openai_base_url`, a private custom-only `model_catalog_json`, and disabled WebSockets/request compression. These routing, catalog and transport overrides belong exclusively to this profile, never root `config.toml`. The catalog contains no API keys. Selections and provider/reasoning edits do not rewrite it. The existing official file-backed authentication is shared, never copied into another home or credential file. Launch with `--no-daemon --profile codex-switch` to keep the custom process separate from the normal client. The wrapper uses generic client instructions, no asserted context-window size, no hosted-tool extensions and image-envelope support; the gateway refuses image input for a backend that does not declare it. Actual upstream limits still apply; history is never silently truncated to fit.

Recent Codex versions reject a chat when its saved provider identity differs from the current provider. Migrating an older `codex_switch_router` connection can therefore affect which provider-pinned chats it can reopen. Preserve old aliases and histories without rewriting them or bypassing the identity check. Native OpenAI chats belong in normal Codex; cross-provider continuation may require the readable handoff below. Retained legacy recovery receipts do not authorize keeping a root gateway override active.

Workspace-enforced routing, keyring-only authentication, API-key-only dashboard startup and external production provider compatibility require their own acceptance evidence. A separate native desktop launch with this profile is not supported. Native terminal/UI acceptance and default-client independence must be verified separately from compilation and fictional contracts. Do not bypass managed policy or replace the owner's running client to verify them.


## Continue a chat with encrypted history

New Switch-managed compactions continue in the same chat when changing models or providers. The gateway asks the current source model for a visible plain-text task summary with tools disabled, stores it encrypted in `model-history.vault`, and returns a local opaque checkpoint token. On subsequent requests the gateway replaces only that token at its original input position with the confirmed summary. Later user messages, tool outputs and images remain in their original order and the on-disk chat remains unchanged. Both legacy `/responses/compact` and native `/responses` compaction-trigger requests use this path. A summary is a separate source inference request and uses that provider's normal allowance.

For an older provider-encrypted checkpoint, Switch records the exact source model/credential identity from completed opaque output events. A native OpenAI checkpoint predating that receipt can be matched exactly to an original local rollout owned by the same signed-in account, including an earlier segment of the same thread. Only the verified source receives its ciphertext to generate the portable summary; the selected destination receives readable context. Confirmed summaries are reused after restart. Returning to a recorded original source does not remain blocked merely because the conversation previously crossed routes.

Missing source credentials, changed sign-in, unknown provenance, missing local checkpoint storage, over-limit summaries and incomplete source responses stop before sending context to the destination. Summary reservations persist before transmission: an automatic duplicate cannot repeat an unconfirmed source request, while a new explicit turn can retry. Existing checkpoint entries are never silently evicted at the bounded store limit. Keep private backups of `model-history.vault` with the provider store. A copied opaque item alone cannot recreate a missing summary.

The manual procedure below remains for unverified or unreachable source history. It is no longer required for a checkpoint Switch can safely transfer.

The refusal protects context that only its original provider can read. Switch cannot decode it, and copying the opaque item is not a portable summary.

1. Keep the original chat. In Switch **Models**, expand **Continue an existing chat** and copy the handoff prompt. This copies a fixed instruction only; it does not read or send a chat, access a key, generate a response or change settings.
2. In the original Codex chat, select its original provider and model using the same signed-in account. Paste the prompt and request a readable handoff summary. The original provider generates it using that account's normal allowance; the destination API cannot generate it from the source provider's encrypted compaction.
3. Start a new chat, select the intended destination model and paste the readable summary. Check the provider label before sending. The source chat remains available for reference, and the handoff does not grant new permissions.

If the original native model still receives the refusal, restore the legacy root connection and return to normal Codex with the original account/model. An already-running client may require the owner's normal restart when work is idle to drop its previously loaded override. Use the separate custom terminal for the destination chat. Do not clear compaction, delete the source chat or send opaque history to an unrelated provider.

A refused transition does not change recorded route history. Missing conversation identity, stateful response references and an unverifiable encrypted source still refuse explicitly. Checkpoint tokens are bound to their conversation and signed-in account; restoring or migrating protected stores never grants new task permissions. Fictional source/destination/native tests and real summary acceptance are reported separately in development STATUS.

OpenAI API credits require a provider configured for `https://api.openai.com/v1` and the corresponding OpenAI API key. Selecting an OpenAI-branded model through another service does not change that service's billing destination.

## Verification

The303-check suite uses fictional upstreams and disposable encrypted storage. Reviewed CLI0.167.0-alpha.3.2 verifies concurrent native/custom app servers, actual V2-profile/default exec processes, live model/reasoning changes, bounded custom507/stream recovery, unchanged root/catalog/auth bytes, and exact/already-original/divergent legacy connect/disconnect cases. With Switch stopped, native requests complete and custom requests report a transport error with `willRetry=true`; the test interrupts only its own turn rather than waiting for the CLI retry policy to finish. Expected-version races and lost configuration-write replies are not fault-injected. Earlier combined-picker receipts are historical. Owner installation, real provider acceptance and interactive terminal acceptance are not established by these fixtures.
