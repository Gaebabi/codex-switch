# Persistent folder index

The1.45.5 release's directory/allocation cache exists only in memory. A new Switch process discards it, and watcher connection resets the root again. Large first scans therefore repeat after every restart. Its drive activity flag also covers the whole traversal, including cached work, so a busy tree can appear to spin without making visible progress. The local follow-up corrects those lifetimes.

The requested correction keeps a private per-application SQLite index outside the account vault. Directory records, file identities/allocated bytes, completed readings, pending invalidations and Windows change-journal cursors commit together. Completed directory work is checkpointed during an initial scan, so closing the window or process preserves progress. Initial allocation measurement remains necessary once; it must not silently omit files or relax sparse/compressed, hard-link, reparse and partial-state rules.

On Windows, use the SDK's FSCTL_READ_UNPRIVILEGED_USN_JOURNAL through a FILE_TRAVERSE volume handle. Check journal identity and retained cursor bounds before replay. Map changed parent/file identities to indexed directories; invalidate aliases as well as the reported parent. Journal loss, replacement, unsupported records or changed root identity cannot certify an old index as current. Filesystem notifications wake the indexer and cover live updates; replay checkpoints preserve changes across process exits and watcher gaps. Index-owned writes must not invalidate the index indefinitely, while their physical allocation remains accounted for.

Index work runs in bounded cancellable slices under the existing global metadata budget, with immutable progress readings. Cache hits and idle waits are not scan activity. Every completion, cancellation and failure clears activity and publishes it. Keep hidden/minimized recursive work paused and retain lightweight capacity/I/O monitoring.

The owner requires all current local drives to be usable and a discoverable permission flow for other users. Probe capability without elevation. Display a lock and explanation only when access or journal activation needs approval. The lock action starts a narrow elevated setup operation, not the account app as administrator; it creates/enables the selected local NTFS change journal and exits. Re-probe from the ordinary process before removing the lock. Cancellation and failure retain saved data and stop the busy indication. Unsupported filesystems and remote journal APIs must be identified separately from permissions, with explicit cached/manual-refresh state rather than a false fresh reading or repeated UAC prompts.

Owner observation initially found ordinary read access on C: and E:, and an inactive journal on D:. The owner explicitly requested support for all current drives plus a discoverable lock and approval action for future users. The narrow setup completed successfully on D:, and an ordinary-token read now succeeds on all three configured local volumes. Original owner data and Codex/backend processes remain intact. The first personal-tree index has not been claimed complete: hidden startup is paused, and first visible work resumes its checkpoints when closed. The owner subsequently approved formal1.45.6 publication, host/VM installation, normal Codex restarts and obsolete-version cleanup; [the release guide](RELEASE_1_45_6.md) records those separate gates.

Verification must cover restart with no unchanged-tree enumeration, offline create/write/rename/delete and hard-link changes, partial-scan restart, journal identity/gaps, root replacement/reparse, hidden cancellation/resume, index self-write behavior, eventual idle activity, permission required/cancel/success/failure and unsupported volumes. Use disposable files and native ordinary-user Windows checks; preserve the owner's accounts, providers, settings and running Codex/backend processes.
