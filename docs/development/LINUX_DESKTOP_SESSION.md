# Local Linux desktop-session verification

[Issue68](https://github.com/Gaebabi/codex-switch/issues/68), within #5/#6/#7, tests a complete reviewed x64 installation candidate through an actual normal-user Debian13/Xfce X11 userspace session on Docker Desktop. It includes xfce4-session, xfwm4, the panel, a private D-Bus and GNOME Keyring. [Xfce session manager](https://docs.xfce.org/xfce/xfce4-session/start). This is additional local acceptance beyond the fresh minimal-image package checks; verification is pending until source-bound receipts and inspected actual program images are attached.

Use a clean committed checkout, the complete reviewed x64 candidate directory and the checksum-pinned original official upstream Debian package. The latter is a local verification input only and is never redistributed with Codex Switch:

```text
python scripts/run-local-linux-desktop.py --packages <candidate-directory> --upstream-package <original-official-amd64.deb> --output artifacts/<fresh-session-results>
```

The orchestrator verifies package hashes, candidate capability/source provenance, actual engine architecture and unchanged production/test source. A separate pinned .NET SDK stage compiles the existing production contract executables; the runtime desktop image contains self-contained executables and no global .NET host/SDK/runtime. Inputs are explicitly selected public tracked source and verified packages. Runtime has no host mounts, Docker socket, published ports, host IPC, personal environment/credentials or networking. The container uses UID1000, all capabilities dropped, two CPUs, 2GiB RAM and a PID limit. Chromium needs Linux user-namespace syscalls; the disposable container's outer seccomp profile is unconfined while the original client sandbox stays enabled. No privileged mode, `--no-sandbox` or production trust relaxation is allowed.

Inside a fresh private HOME/XDG/session, the test installs the actual per-user package and invokes its normal desktop entry. It exercises the ordinary program's native own-XID window at multiple sizes, refresh, close and reopen. It does not pass `--verify-ui`, import fake accounts or inject an account-switch/resumption result. Existing production native contracts verify actual encrypted key/vault roundtrip, concurrency, lock/unlock and original-key/ciphertext preservation after provider restart, plus two original sandboxed official-client start/IPC/normal-close cycles and preservation of an independent actual CLI. Screenshots establish actual visible UI only; native receipts establish nonvisual contracts.

Only selected own-window PNGs and scoped receipts may be exported. Strip image metadata, validate dimensions/entropy/hash, visually inspect every selected image and exclude raw diagnostics/fixture homes from GitHub. The orchestrator verifies the original ID/name/label/mount boundary before removing only its own container; results remain in ignored artifacts. Other containers and installed applications are untouched.

The native Linux workflow also runs this additional desktop session on its actual x64 worker after complete package verification. Only PNGs and the scoped session receipt enter the `desktop-session-linux-x64` CI artifact; raw logs and private homes are excluded. ARM64 retains its separate native provider/client/package gates and does not claim this x64 desktop-session result.

Docker Desktop runs these userspace processes on its Linux VM kernel; this is **not a booted desktop VM**. [Docker's container/VM distinction](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/). Display uses X11/Xvfb with a real session/window manager, not a native GPU/physical monitor. Login manager/PAM, GNOME/KDE sessions, XWayland/pure Wayland, accessibility/scaling, ARM64 and authenticated account switching/same-chat/one-Continue remain separate gates. Ordinary Linux account/handoff integration is still gated; no existing personal account/token is copied and no new stable Release is published.
