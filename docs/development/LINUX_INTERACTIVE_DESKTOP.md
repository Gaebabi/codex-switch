# Owner-operated Linux desktop acceptance

[Issue76](https://github.com/Gaebabi/codex-switch/issues/76) continues #5/#6/#7 with direct owner authentication. This is an optional local verification tool, never an account-bearing CI job or a supported Linux Release. The [offline desktop recipe](LINUX_DESKTOP_SESSION.md) must first produce the reviewed native x64 desktop image.

```text
python scripts/run-interactive-linux-desktop.py --desktop-image codex-switch-desktop-session:<verified-12-hex-revision> --output artifacts/<fresh-private-interactive-session>
```

The runner compares the base candidate's committed production/test inputs with the clean checkout and builds only selected public overlay files. A unique temporary local tag binds the verified base image ID for BuildKit; every original immutable base layer and the tag's unchanged ID are checked before running the resulting immutable image. Only that temporary tag is removed. Image stores may report a config digest that BuildKit cannot resolve as a registry manifest; no registry pull or guessed digest substitutes for the local base. Inspect `owned-container.json` for the exact IDs, revisions and isolated bridge network. `viewer-private.json` contains temporary local viewer access material: open its URL locally, never paste it into an issue, PR, CI artifact or public screenshot. The password is in the URL fragment, which the browser does not send in HTTP requests. [noVNC embedding documentation](https://novnc.com/noVNC/docs/EMBEDDING.html).

Only `127.0.0.1:<allocated-port>` is published on the host. VNC itself listens on container loopback and requires a random per-start password; its clipboard exchange is disabled. The container runs UID1000 with all capabilities dropped, private IPC, bounded CPU/RAM/PIDs and no host mounts or devices. The private bridge permits outbound official authentication; other project networks are not joined. The original Chromium sandbox stays enabled. As in the offline recipe, the outer seccomp profile permits its actual user-namespace sandbox; privileged mode and `--no-sandbox` are not used.

The actual Xfce session/window manager/panel, Firefox, private file-socket D-Bus and installed application run in a new0700 HOME. Display variables are present before D-Bus starts and in its activation environment, allowing real Secret Service password prompts. With no default collection, a helper requests the provider's native creation dialog and retains the same connection until it completes. The owner chooses the test-keyring password directly; the helper never receives it. The ordinary app starts after this step. Existing collections and keys are not replaced or automatically unlocked; use the native **Passwords and Keys** application for a locked keyring, then Refresh. Creation requires one retained D-Bus connection: separate short-lived `gdbus` processes invalidate the original caller's prompt.

Use the ordinary app's **+** button to authenticate each owner-controlled test account in Linux Firefox. Neither host-browser cookies nor Windows Codex credentials are imported. Keep authentication outside all captures. Once both accounts are registered, verify actual active identity, Start Codex ownership, manual Switch followed by automatic completion, original chat/folder/model/permission preservation, a single eligible Continue and encrypted recovery/cancellation. Observe real product state; never inject the expected action/result through a fixture API. Public evidence contains only individually inspected, irreversibly sanitized own-window screenshots and scoped semantic receipts.

Closing the viewer or runner does not delete the container or its private data. Preserve `owned-container.json` and the owner-created keyring password locally to resume later. Before stopping a session, normally quit its Codex client and utility in the remote desktop. Cleanup requires checking the exact recorded ID/name/label/mount boundary; never prune Docker globally or remove another project's container, network or home. Do not export or commit the session filesystem, account vault, browser profile, keyring, password file or raw logs.

Docker/Xvfb X11 userspace does not prove a booted desktop VM, PAM/login manager, full GNOME/KDE, native GPU, XWayland/pure Wayland, ARM64, scaling or accessibility acceptance. Record these separately before promoting supported downloads.
