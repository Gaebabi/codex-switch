# Native desktop model integration

The Windows desktop backend combines the original native `model/list` response with the registered fixed custom aliases. OpenAI inference still goes directly from the original Codex engine to its configured OpenAI destination. The Switch window is an editor for registrations and visibility; neither native requests nor the desktop backend lifetime depends on that window staying open.

This supersedes the separate-terminal-only restriction for the native picker. The old combined HTTP profile remains retired: never install a root `openai_base_url`, root provider, or root catalog override for this integration. The separate V2 terminal profile remains available as an independent legacy workflow.

## Components and installation

The Windows package includes `backend/CodexSwitch.Backend.exe`. Configure it with `--configure <exact Switch data directory> <Codex home> <original Codex executable>`. Configuration requires the reviewed native CLI `0.167.0-alpha.4.1` and validates its generated catalog in a credential-free home before enabling integration. Stable `0.167.0` has a different native tool contract and is not interchangeable with this desktop build. Incompatible engines are refused before changing the catalog or protected settings. The exact original data directory matters for packaged-parent installations; do not substitute an empty default LocalAppData store.

The desktop's supported `CODEX_CLI_PATH` launch override selects the backend executable. Record and preserve any prior override when installing. One initial normal same-account Codex restart activates the new executable. Subsequent model registration, selection, visibility changes, deletion, and Switch window restarts require no Codex restart. Restore only the recorded owned launch override when uninstalling; preserve native configuration, authentication and chat files.

For a fresh Windows installation, extract and keep the complete versioned ZIP in a writable user-owned directory. Close the Switch editor normally before configuration. Use its existing `--data-dir` and `--codex-home` arguments to identify the actual stores; the default LocalAppData path can differ from a packaged parent's active directory. Select the original native `codex.exe`, never another adapter. Run:

```powershell
& '<installation>\backend\CodexSwitch.Backend.exe' --configure '<existing Switch data directory>' '<existing Codex home>' '<original codex.exe>'
```

After successful validation, record the existing user/process `CODEX_CLI_PATH` values privately and set that user environment variable to the absolute `backend\CodexSwitch.Backend.exe` path. Launch Switch with the same data/home arguments and that environment value, then perform the one initial normal same-account Codex restart when its work is idle. Verify the combined menu before using a custom model. Do not edit root `openai_base_url`, credentials or history.

For later version upgrades, keep the old installation available while its backend is running. Verify the new complete released package, reuse the existing validated backend bootstrap with the exact original native executable, data directory and home, and update only the owned launch override and launchers. Preserve the owner's routing/backend enabled flags, model visibility, defaults and context settings. Do not repeat `--configure` merely to install a new version: that command enables the initial connection and changes protected settings. Confirm the new loaded backend and its actual catalog acknowledgment after an authorized normal restart. The running backend continues receiving ordinary catalog changes without replacement.

The adapter owns an original native app-server child for the lifetime of Codex. It relays native requests, server requests, responses and notifications, and negotiates the experimental APIs needed for scoped conversation settings. The child is in an owned Windows process job so an interrupted adapter cannot leave an inference process behind. The custom-only HTTP gateway starts lazily inside this backend, never as a machine service or a global OpenAI proxy.

The desktop sends JSON-RPC stdin as UTF-8. The adapter reads the raw stream using an explicit strict UTF-8 decoder rather than `Console.In`, whose default on Windows can use a legacy console code page. The old default could corrupt user prompts and automatic question replies before they reached either model, while JSON-escaped output remained readable. Invalid UTF-8 now fails instead of silently replacing characters. This does not change Windows regional settings or rewrite existing chats. Verification sends both literal multilingual UTF-8 and ASCII-escaped Unicode through the actual executable; ordinary .NET JSON serialization escapes non-ASCII characters and previously concealed the defect. Applying this executable change to an already running adapter requires a normal idle installation restart; subsequent model operations retain their restart-free behavior.

## Live model lists

Switch validates custom metadata through the actual native catalog parser, writes an immutable catalog revision, then atomically publishes `desktop-backend-catalog.json`. This file contains model metadata and paths, never provider credentials. Normal OpenAI requests do not read the provider vault. Model-list pagination uses bounded snapshots and preserves native entries, defaults and metadata. Only custom entries are appended; their `isDefault` flag is false.

The existing desktop IPC model-query invalidation refreshes the native picker. A currently mounted menu can retain its rendered snapshot until it is reopened; reopening the menu is not a client restart. `desktop-backend-observed.json` acknowledges a revision only after the last page of that list has been written to the client. A saved file alone is not a confirmed desktop refresh. Labels include both upstream model and provider name so identical upstream IDs remain distinguishable. Hidden aliases remain routable for existing chats. Removed aliases fail explicitly and are never redirected to a different provider.

Desktop custom catalogs declare `tool_mode="code_mode_only"` and `supports_search_tool=true`. These are native tool presentation/discovery capabilities: the native engine exposes code execution and discovers deferred app tools as needed. Both fields are necessary; enabling a general code-mode feature alone still expands account-enabled app schemas into the request. A synthetic request through the actual native engine measured about 497 KB before and 46 KB after this correction. Tools and the provider's real context limit are retained. Native model metadata is untouched. Verify the actual request protocol and real tool execution, rather than disabling tools or enlarging the advertised context to hide the failure.

### Tool capability boundaries

Tool discovery and image-input metadata do not guarantee successful tool execution. A registered model must produce valid arguments and complete the actual operation. The documented `exec` to `node_repl` to `@oai/sky` route can operate native desktop apps; browser control also depends on the installed browser tool and its URL-policy checks. A browser-policy refusal is a blocked test, not a successful navigation, and must not be bypassed.

Built-in OpenAI image generation is currently unavailable in custom-model chats. Its image request follows the conversation's scoped `openai_base_url`, and the desktop's custom-only gateway explicitly refuses `/images/generations` and `/images/edits`. This is a routing boundary, independent of reasoning effort or the model's ability to call `image_gen__imagegen`. Native OpenAI chats keep their direct routing. Supporting images from custom chats requires a separate native image route while retaining that separation; removing the custom-only boundary or installing a root OpenAI proxy is not the solution.

Acceptance reports must inspect tool results and returned artifacts. A completed turn can report failure, and a success-marker string can appear inside a sentence denying success. Neither a completion event nor a substring match is sufficient to pass a capability test.

## Conversation routing and history

### Context size and automatic compaction

On Windows, open Switch's model settings and expand **Context and auto compaction**. Select **OpenAI (all native models)** for shared native defaults, or a registered model for an independent override. Enter positive whole token counts for the context window and automatic compaction threshold, then save. Empty fields restore the original configuration/provider defaults. The threshold cannot exceed the entered window. Model capacity and the native engine's safety margins still apply; these controls do not expand an upstream model's actual capacity.

Settings are stored in the existing encrypted provider store and published with the catalog revision. The backend passes `model_context_window` and `model_auto_compact_token_limit` only in the selected conversation's configuration. It never changes root configuration or sends native OpenAI HTTP through Switch. The next request in an already loaded conversation uses the new values through the same-ID unload/resume path; an active response finishes with its original settings. Neither model setting requires a Codex restart. The Windows backend must include this feature; an already running older executable keeps its prior behavior until the next ordinary launch selects the upgraded backend.

The native-engine contracts verify reported context sizes, automatic compaction after lowering a threshold, default restoration, changes during an active request, direct native routing and unchanged backend/native process identities. Production Windows controls are tested with fictional data in Korean and English.

Custom conversations use the original `openai` provider identity with thread-scoped `openai_base_url` and `model_catalog_json` overrides. Native conversations use their original configuration. A model name alone cannot change a running native session's endpoint: the adapter unsubscribes the idle conversation, waits for confirmed unload, then resumes the same ID with its new scoped configuration and restores its settings. The native process is not restarted. Requests are serialized per conversation so unrelated native chats remain available during a handoff; active turns keep their existing destination.

Desktop model-picker persistence is scoped too. The desktop sends ordinary configuration writes when remembering a model; forwarding a custom `cs_...` alias into the shared `config.toml` breaks a separately launched native CLI. The backend keeps custom model/reasoning defaults in the existing encrypted provider store, exposes them only to desktop configuration reads and new desktop conversations, and leaves native defaults intact. Both single-value and batch writes retain the native configuration writer's version/policy checks; unrelated settings still use that writer. Selecting a native default clears the desktop-only choice. Existing conversations retain their own model and history.

Ephemeral sessions have no durable resume contract, so a connection handoff is refused before unloading them. Start such sessions with the intended model. Ordinary desktop chats retain their original IDs and history.

Before a custom conversation returns to native OpenAI, the existing native-history recovery preflights any Switch-owned checkpoint, verifies its exact account/conversation/segment binding and source summary, and performs official native compaction. It requires durable native replacement before allowing ordinary native inference. Neither SQLite nor rollout bytes are edited. Missing source summaries and changed histories remain visible failures. Opaque native compaction output is never replaced by a manufactured Switch token.

This boundary also applies to provider-specific reasoning that is stored as plaintext `reasoning.content`. OpenAI can reject that input even when the selected reasoning effort is valid. Preflight identifies active custom reasoning from recorded custom turns and fingerprints its content. The temporary compaction-only request excludes only the matched foreign reasoning state; original native reasoning, user/assistant messages and tool calls/results remain. Official compaction durably replaces the active context, while the old rollout bytes stay intact. A changed fingerprint stops recovery. This conversion is needed only when active nonportable state remains; repeating a completed handoff performs no additional recovery inference. Normal native requests continue to use direct OpenAI HTTP.

Foreign tool output items have a separate optional `id` whose format can be invalid for the corresponding native item type. That ID is not the `call_id` joining a call to its result. The same provenance/fingerprint preflight identifies foreign function/custom tool items, including turns with no reasoning. Only their optional item IDs are omitted during official compaction; their names, arguments/input, `call_id`, results and all native IDs remain unchanged. A changed call body stops preflight. Message IDs do not trigger this tool-ID conversion.

The provider and history stores reload their latest protected state and serialize write transactions across backend and editor instances. A saved provider edit must not be overwritten by a concurrent successful-route receipt, and a second history writer must preserve the first writer's checkpoint.

## Verification

Native side chats created by `thread/fork` can reference an ordinary parent rollout through `history_base`. Recovery distinguishes that conversation ancestry from rollover segments that retain the current conversation ID. Each parent uses its own verified metadata ID, the original account/provider and the recorded byte boundary. Ambiguous parent candidates, cycles, escaping links and invalid bounds remain failures. Parent and child rollout bytes are never rewritten to make preflight succeed. Contracts cover bounded multi-level forks and actual-native backend fork/read without additional inference.

Responses Lite history can contain several `additional_tools` items for the same namespace, each carrying only changed members. They are ordered historical updates, not conflicting current definitions. Custom catalog entries explicitly select standard Responses (`use_responses_lite=false`), which makes the native engine supply the full current top-level `tools` array. Custom routing preserves that array verbatim and consumes the historical catalog controls without restoring obsolete tools. An explicit empty array remains empty; a missing current catalog or malformed historical control is refused. Messages, calls and results remain in their original order, and native OpenAI traffic is unchanged. The actual-native backend fixture resumes a synthetic history with repeated namespace updates through official RPC before switching native/custom/native; it does not edit an owner's rollout.

The reviewed engine can carry a turn's reasoning change in an input `configuration_update` while retaining the session's initial effort at the top level. Custom routing applies these ordered reasoning updates before validating the effective effort, then consumes the applied control items from the upstream input. Conversation messages, reasoning history and tool calls remain intact; native OpenAI requests retain their original protocol. Unknown configuration fields are refused rather than discarded. Regression fixtures include a native `max` default followed by a custom turn with a different supported effort.

Native history preflight resolves the configured `sessions` and `archived_sessions` directory links before comparing rollout locations. The native database may store the physical path while callers retain its home-directory alias; both identify the same authorized storage. Parent segments remain bounded to those roots with account, thread, cycle and byte-boundary checks. Unrelated locations and nested links that escape the configured roots remain invalid. Ordinary chat text mentioning a portable checkpoint is not itself a compaction record. Owner histories are neither moved nor rewritten for this normalization.

Run the model-provider test executable with `--backend-only --codex <reviewed native CLI> --backend <published backend executable>`. Its disposable homes and fictional HTTP upstreams exercise the real app-server, combined pagination, native/custom routing in one conversation, visibility, addition/deletion, exact credential routing, process identity, editor shutdown independence and unchanged root configuration/authentication. Run the existing provider and native recovery suites after storage/history changes.

These contracts are separate from installed native picker inspection, real provider inference, the one authorized owner installation, and public release. The current implementation is reviewed against native CLI `0.167.0-alpha.4.1`; a future native protocol change requires renewed compatibility validation, not a silent root HTTP fallback.
